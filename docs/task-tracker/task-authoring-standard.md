# Регламент задач VibeRadar Task Tracker

Этот документ задаёт контракт для людей и Codex-навыка `viberadar`, который раскладывает крупную работу на задачи в `viberadar.tasks.json`.

## Цель

VibeRadar должен быть рабочим списком задач, а не складом заметок. После ревизии, рефакторинга или аудита проекта агент должен создать набор конкретных задач, которые можно брать в работу из интерфейса VibeRadar без дополнительного переписывания.

Целевой поток:

1. Пользователь формулирует крупную цель: например, «разложи рефакторинг авторизации».
2. Codex-навык `viberadar` анализирует проект, классифицирует намерение, источники, результат и побочные эффекты.
3. Навык создаёт или импортирует задачи в `viberadar.tasks.json`.
4. Пользователь нажимает в интерфейсе VibeRadar «Взять в работу».
5. VibeRadar запускает агента с подготовленным промптом, переводит задачу в `in-progress`.
6. После успешного завершения агента задача переходит в `done`; при ошибке — в `review`.

## Формат файла

Источник истины — файл `viberadar.tasks.json` в корне проекта.

```json
{
  "version": 1,
  "updatedAt": "2026-05-06T12:00:00.000Z",
  "tasks": [
    {
      "id": "refactor-auth-session-boundary",
      "title": "Разделить работу с сессией и HTTP-ответом",
      "description": "Сейчас обработчик авторизации смешивает проверку сессии, чтение cookies и сбор HTTP-ответа. Нужно вынести границы ответственности, чтобы упростить тестирование.",
      "prompt": "Проведи точечный рефакторинг авторизации. Сначала найди обработчики входа и проверки сессии. Раздели чтение сессии, доменную проверку и сбор HTTP-ответа без изменения публичного поведения. Не меняй схему данных. После правок запусти релевантные проверки.",
      "status": "backlog",
      "priority": "high",
      "type": "refactor",
      "featureKey": "auth",
      "filePaths": ["src/server/auth.ts", "src/server/session.ts"],
      "tags": ["refactor", "auth", "session"],
      "acceptanceCriteria": [
        "Публичное поведение авторизации не изменилось",
        "Логика сессии выделена из HTTP-обработчика",
        "Релевантные тесты или проверка типов проходят"
      ],
      "source": "review-import",
      "order": 1000,
      "createdAt": "2026-05-06T12:00:00.000Z",
      "updatedAt": "2026-05-06T12:00:00.000Z"
    }
  ]
}
```

## Поля задачи

Обязательные поля:

- `title`: короткое название на русском языке, глагол + объект, до 180 символов.
- `description`: зачем задача нужна, какой риск или проблема закрывается.
- `status`: `backlog`, `todo`, `in-progress`, `review`, `done`, `archived`.
- `priority`: `low`, `medium`, `high`, `urgent`.
- `type`: `bug`, `feature`, `test`, `docs`, `observability`, `refactor`, `chore`.
- `filePaths`: массив относительных путей, если область известна; пустой массив допустим только для исследовательских задач.
- `tags`: короткие метки для поиска.
- `acceptanceCriteria`: проверяемые критерии готовности.
- `source`: `manual`, `review-import`, `agent-run`, `scan-finding`.
- `order`: число для сортировки внутри колонки.

Опциональные поля:

- `id`: стабильный человекочитаемый ключ латиницей. Если не указан, VibeRadar создаст его сам.
- `prompt`: готовая инструкция агенту для кнопки «Взять в работу».
- `featureKey`: ключ фичи из `viberadar.config.json`, если задача привязана к фиче.
- `lastRunId`: последний запуск агента, заполняется VibeRadar.
- `completedAt`: время завершения, заполняется при `done`.

## Как писать хорошие задачи

Одна задача должна быть атомарной: один результат, один понятный набор файлов, один способ проверить готовность.

Хорошая задача:

- меняет один слой, один модуль или одну связку модулей;
- помещается в один запуск агента;
- содержит контекст, но не требует читать внешний отчёт;
- имеет критерии приёмки, которые можно проверить командой, тестом, типами или ручным просмотром;
- не зависит от конкретной формулировки исходного запроса.

Плохая задача:

- «поправить всё в авторизации»;
- «посмотреть код и улучшить»;
- «сделать как в отчёте выше»;
- «переписать проект»;
- задача без критерия готовности.

## Декомпозиция больших работ

Если ревизия рождает десятки или сотни задач, навык должен сначала классифицировать весь объём:

- намерение: рефакторинг, исправление ошибок, тесты, документация, наблюдаемость, производительность;
- источник: статический анализ, ревизия кода, пользовательский отчёт, падение тестов, ручное наблюдение;
- требуемый результат: кодовая правка, тест, документ, проверка, удаление долга;
- побочные эффекты: миграции, изменение публичного API, риск регрессии, затрагивание данных.

Затем задачи группируются по фичам, модулям и риску. Для 100 задач нормальная структура такая:

- 5-15 задач `urgent` или `high`: блокеры, риски данных, безопасность, падения тестов, критические регрессии;
- 30-50 задач `medium`: полезные, но не блокирующие улучшения;
- остальные `low`: долг, чистка, документация, необязательные улучшения.

Не надо создавать 100 задач одного приоритета. Если приоритеты не различимы, декомпозиция сделана плохо.

## Приоритеты

`urgent`:

- данные теряются или портятся;
- сборка, запуск или ключевой сценарий не работает;
- безопасность, доступы, платежи, критические интеграции;
- задача блокирует десятки следующих задач.

`high`:

- высокий риск регрессии;
- важный пользовательский сценарий;
- заметно снижает стоимость дальнейшего рефакторинга;
- закрывает нестабильность тестов или наблюдаемости.

`medium`:

- локальное улучшение качества;
- добавление тестов к важной, но не критичной зоне;
- понятный технический долг без немедленного риска.

`low`:

- косметика, переименование, мелкая чистка;
- документация без срочного операционного риска;
- улучшения, которые легко отложить.

## Подготовленный промпт

Поле `prompt` должно быть написано так, чтобы агент мог выполнить задачу без чтения исходного отчёта.

Структура промпта:

1. Цель: что изменить.
2. Границы: что нельзя менять.
3. Контекст: почему задача существует.
4. Файлы или области поиска.
5. Ожидаемый результат.
6. Проверки.

Шаблон:

```text
Выполни задачу: <краткая цель>.

Контекст:
<почему это нужно>

Границы:
- Не меняй <контракт/API/схему/поведение>.
- Не хардкодь под конкретный документ, домен или формулировку.
- Если обнаружишь риск шире задачи, зафиксируй его, но не расширяй правку без необходимости.

Файлы/область:
- <path>

Что сделать:
- <конкретные шаги>

Критерии готовности:
- <проверяемый результат>

Проверки:
- <команда или тип проверки>
```

## Правила для Codex-навыка `viberadar`

Навык должен возвращать только структурированный JSON: массив задач или объект `{ "tasks": [...] }`.

Запрещено:

- возвращать Markdown вместо JSON;
- ссылаться на «отчёт выше» как на единственный источник;
- создавать задачи без `description`, `prompt` и `acceptanceCriteria`;
- хардкодить решения под один документ, домен или формулировку;
- смешивать несколько независимых правок в одной задаче;
- создавать задачи, которые требуют уточнения у пользователя перед каждым запуском.

Алгоритм навыка:

1. Изучить цель пользователя и проектный контекст.
2. Классифицировать намерение, источники, результат и побочные эффекты.
3. Сформировать список задач с русскими названиями.
4. Присвоить приоритеты по риску и зависимости.
5. Для каждой задачи подготовить автономный `prompt`.
6. Отсортировать задачи: `urgent`, `high`, `medium`, `low`; внутри — по зависимостям.
7. Вернуть JSON, пригодный для импорта в VibeRadar.

Минимальный ответ навыка:

```json
{
  "tasks": [
    {
      "title": "Добавить тесты на ошибку восстановления сессии",
      "description": "Ревизия показала, что ветка восстановления сессии не покрыта тестом, поэтому регрессия может остаться незамеченной.",
      "prompt": "Добавь тесты на ошибку восстановления сессии. Найди существующие тесты auth/session, добавь проверку неуспешного восстановления без изменения публичного API. После правок запусти релевантный тест или проверку типов.",
      "status": "backlog",
      "priority": "high",
      "type": "test",
      "featureKey": "auth",
      "filePaths": ["src/server/session.ts"],
      "tags": ["auth", "session", "tests"],
      "acceptanceCriteria": [
        "Есть тест на неуспешное восстановление сессии",
        "Существующие успешные сценарии сессии не сломаны"
      ],
      "source": "review-import",
      "order": 1000
    }
  ]
}
```

## Жизненный цикл

- `backlog`: задача создана, но ещё не запланирована.
- `todo`: задача выбрана в ближайшую работу.
- `in-progress`: пользователь нажал «Взять в работу», агент запущен или задача выполняется вручную.
- `review`: агент завершился с ошибкой или задача требует проверки человеком.
- `done`: агент успешно завершил выполнение или человек явно отметил задачу готовой.
- `archived`: задача больше не нужна.

Для автоматического исполнения VibeRadar использует `prompt`. Если `prompt` отсутствует, VibeRadar соберёт базовый промпт из полей задачи, но для задач из ревизии это считается ухудшением качества.
